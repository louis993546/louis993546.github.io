Let’s get back to the main course!</em></p><hr><h2 id="what-it-is">What it IS?</h2><h3 id="part-1-a-way-to-bring-reactive-programming-model-to-native-android-development">Part 1: a way to bring “reactive programming model” to native Android development</h3><p>React.js got released to public in 2013, while it took some convincing, it ultimately popularize the idea of “UI as code”/“Declarative UI”.</p><p>In a very simplified term: you can think of it as “data binding on steroid, powered by a real programming language”: instead of having xml/html templates + Java/Kotlin/JS code to manipulate the layout, you just mesh the 2 things together. And since now they are together, instead of “hey, that TextView/Label/&lt;p&gt;, change the text to <em>The talk is 13 days away and you are so screwed</em>”, all a component needs to do is “This is the message, now put it on screen”.</p><p>(Again, hugely simplified here ☝️)</p><h3 id="part-2-a-new-unbundled-toolkit-to-make-part-1-possible">Part 2: a new “unbundled toolkit” to make Part 1 possible</h3><p>In order to make this new programming paradigm possible (or at least to not kill more Android developer than it have already), a bunch of new stuff are build, not only to make it possible, but to create a good user (development) experience as well.</p><h2 id="what-it-looks-like">What it LOOKS LIKE?</h2><!--kg-card-begin: html--><script src="https://gist.github.com/louistsaitszho/a93ad5c0b0819b9a3c5d7793acc81267.js"></script><!--kg-card-end: html--><p>Translation: There is a widget call Greeting, it has 1 property: name, and what it does is “it draw a modified version of name onto the screen (somehow)”.</p><h2 id="why"><strong>WHY?</strong></h2><!--kg-card-begin: html--><iframe src="https://www.youtube.com/embed/VsStyq4Lzxo?feature=oembed" width="700" height="393" frameborder="0" scrolling="no"></iframe><!--kg-card-end: html--><p>TL;DR:</p><ul><li>Existing UI framework is design in the Java 1.4/5 world</li><li>Some design decisions age badly</li><li>React/flutter/${insert yet another React-inspire framework here} shows the world what “UI as code” can be in 2018+</li><li>Kotlin is (one of) the last piece of puzzles to trigger them to rethink what Android UI framework can be in 2018+</li></ul><h2 id="what-is-the-toolkit-made-of">What is the toolkit made of?</h2><h3 id="1-runtime-we-will-talk-about-it-next-time">1. Tooling</h3><p>At the time of the writing, there is not much to talk about. It’s definitely something they are aware of, but at this point “getting the code works” is a much higher priority. The 1 thing that just comes automatically from the paradigm is that since UI is code, you can now very easily debug it already 🎉 Put a break point works, you can see what exact color/padding/margin/whatever parameter/component is being instantiated, and what value is being pass to it 👍</p><p>(Side note: IMO what Xcode has for SwiftUI looks awesome 🤤)</p><hr><h2 id="in-a-very-simplified-version-how-does-each-component-draw-stuff-if-it-s-not-a-android-view-view">In a very simplified version, how does each “component” draw stuff if it’s not a android.view.View?</h2><p>There is no black magic or anything crazy: it just use a (slightly abstracted version of) canvas. For example: Text (~ android.widget.TextView)</p><!--kg-card-begin: html--><script src="https://gist.github.com/louistsaitszho/c6bfd8e6b99b9095118524883648f651.js"></script><!--kg-card-end: html--><p>So it does <strong>NOT</strong> use View (with a few exceptions), it re-implements a lot of the basic building blocks of UI, which is why it’s “unbundled”. But other than that, it’s also nothing too special or magical.</p><p>(Why it abstracted canvas? Maybe cross-platform? Or maybe just to make it easy to test on even normal JVM? 🤷)</p><h2 id="on-the-other-side-of-the-spectrum-how-does-it-get-that-canvas-how-does-it-get-attach-to-the-traditional-world-of-android-ui">On the other side of the spectrum: how does it get that canvas? How does it get attach to the traditional world of Android UI?</h2><p>Compose ultimately needs to attach itself to a ViewGroup, and that ViewGroup can be attach to wherever you want it to be. In the current implementation, they just created some simple extension function for Activity to make it looks nicer.</p><p>This is one of the other thing that I am obviously simplifying a lot, but that’s also kind of the point of compose to begin with 🤷 I promise I will tell you guys a lot more in the internals of the runtime and compiler, but honestly, binding back to the traditional Android API is just not that interesting to me.</p><hr><p>In the next chapter, I will start digging into “how to create a component”, and why it is structure the way it is (annotation, function with no return type, etc.).
